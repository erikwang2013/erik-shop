## 1. Серверный бизнес-API (service/)

### Сводка текущего состояния
Фундамент инфраструктуры, безопасности/оплаты/поиска/рекомендаций прочен (39 контроллеров + 111 моделей + 14 промежуточных ПО + 10 планировщиков, Stripe/PayPal реально работают, 22 юнит-теста пройдены), но ряд заявленных в документации «полными» возможностей на деле является заглушками или не подключён: шлюзы Klarna/Adyen только сконфигурированы, при оформлении не считаются купоны/доставка/пошлины/фрод-контроль, разделение чтения/записи не включено, бизнес-сиды отсутствуют — из-за чего ключевые интерфейсы после свежей установки не имеют данных.

### Реализовано
- Двойная реализация платёжных шлюзов (реальный код): в PaymentGateway.php Stripe (PaymentIntent + проверка подписи webhook + возврат) и PayPal (REST v2 OAuth2 + заказ/захват/возврат + пятиполевая проверка verify-webhook-signature + разбор capture id возврата) полностью работоспособны; в PaymentController::webhook атомарная защёлка статуса заказа предотвращает двойное зачисление и в транзакции создаётся запись расщепления PlatformSettlements
- Замкнутая платёжная цепочка: PaymentController (create/status/methods/webhook), AdminOpsController::executeRefund реально выполняет возврат через шлюз и транзакционно пишет в БД (заявка на возврат + запись платежа + статус заказа + лог), PaymentReconcileCron каждые 6 часов сверяет по реальному статусу шлюза платёжные записи «ожидает оплаты» старше 2 часов
- Стек из 14 промежуточных ПО действует по порядку (config/middleware.php): Cors→Security(security-php SecurityGuard, 25+ детекторов + счётчики перебора в Redis)→RateLimit(скользящее окно Redis, правила для 6+ конечных точек)→Platform(определение 8 платформ)→GeoIp(MaxMind)→Locale→HashidsDecode→VersionRoute(заголовок API-Version)→HashidsEncode→Encryption, маршрутные PosterVerify/JwtAuth/AdminKey
- Реальная реализация мультивалютного ценообразования и многоязычных товаров: ProductSkuPrices — независимое ценообразование по валютам + деградация курсов ExchangeRates, ProductTranslations — eager load по locale (в ProductController расчёт отображаемых цен с VAT: с налогом/без налога)
- Оценка пошлин реально работает: TariffController по ProductHsCodes→TariffRules(dest_country+hs_code)→VatSettings рассчитывает duty/vat (включая порог беспошлинного ввоза и disclaimer); ShippingController считает доставку по логистическим зонам + ступеням веса
- Реальная реализация поиска и рекомендаций: SearchController через webman-scout (модель Products Searchable + ES-маппинг erik_shop_products), при ошибке ES деградация на MySQL LIKE с записью SearchLogs; RecommendationCron за последние 90 дней считает совместную встречаемость покупок, пишет Top10 в product_recommendations, RecommendationController — item-based CF + деградация на популярное
- Ключевой поток заказов: store в транзакции атомарно списывает запасы (where stock>=qty decrement, защита от перепродажи), отмена восстанавливает запасы, точки перехвата KYC/запрещённых товаров, автомат статусов 0-8; CouponController::claim — строковая блокировка lockForUpdate + атомарная защёлка против перевыдачи
- Все 10 планировщиков зарегистрированы в config/process.php (курсы/отслеживание логистики/Feed/рекомендации/соответствие/таймаут возвратов/напоминания о ценах/сверка платежей/расщепление/мультиплатформенная синхронизация), все с логированием ошибок и логикой пропуска при отсутствии конфигурации
- Реальный экспорт документов: ExportController PhpSpreadsheet XLSX+CSV (включая колонку HS Code), DocumentController — коммерческий инвойс/упаковочный лист (dompdf), HealthController — проверка живучести (двойная проверка db/redis)
- Полный набор инструментов качества: PHPUnit 12.5 (22 tests/45 assertions, 4 файла: Security/Jwt/ApiResponse/RedisFacade), phpstan level 5 (phpstan.neon с исключениями ложных срабатываний Eloquent), php-cs-fixer, .github/workflows/ci.yml (матрица PHP 8.3/8.4 + MySQL + Redis)
- Реально внедрённые инфраструктурные паттерны: снежинкообразные первичные ключи BaseModel, автоматическое преобразование кодирования/декодирования Hashids в промежуточном ПО, пара токенов access/refresh в Jwt.php (JwtAuth отклоняет refresh для бизнес-интерфейсов), шифрование полей encryptable, конфигурации config/risk.php+country.php+geoip.php на месте

### Пробелы
- Klarna/Adyen/Afterpay только заглушки: в match у `PaymentGateway::make()` поддерживаются только stripe/paypal (в default выбрасывается исключение), в PaymentController::methods явный filter возвращает только stripe/paypal (в комментарии признание: «чтобы не выставлять нереализованные шлюзы»); но пример ответа в docs/api.md 6.1 содержит строку Klarna, features.md 1.0 заявляет Klarna BNPL/Adyen — документация расходится с кодом
- При оформлении не интегрированы купоны/доставка/пошлины/фрод-контроль: OrderController::store только суммирует подытог товаров, не читает документированный coupon_id (api.md 5.3), не считает уже существующие в erik_orders поля shipping_fee/tax_amount/discount_amount/insurance_fee; config/risk.php существует, но в app/ нет ни одного вызова RiskEngine (features.md 3.3 заявляет «расчёт цены (по валютам + купоны)» и «фрод-оценка (RiskEngine::score)»)
- Отсутствуют бизнес-сиды: в install.sql всего 2 INSERT (системные таблицы wa_options/wa_roles), erik_hs_codes/erik_tariff_rules/erik_payment_gateway_methods/erik_shipping_zones/erik_countries — все без данных; в database/seeders только countries.php, и ни один код его не загружает (мёртвый файл; CLAUDE.md заявляет покрытие стран/HS Code/курсов/логистических зон/категорий соответствия/таблиц размеров/правил фрод-контроля) — после свежей установки интерфейсы countries/payment methods/доставки/пошлин возвращают пустоту
- Разделение чтения/записи не включено: config/database.php определяет mysql_rw (2 реплики чтения + sticky), но в app/ и config/ нет ни одного обращения к этому имени соединения, все модели используют mysql по умолчанию; заявление features.md 5.x «DB разделение чтения/записи (2 реплики чтения + sticky) полное» не соответствует действительности
- Подписочные покупки и мультиплатформенная публикация — только структура таблиц: модели Subscriptions/SubscriptionOrders/SubscriptionLogs, PlatformListings существуют, но нет контроллеров/маршрутов/кода записи (мультиплатформенность — только PlatformOrderSyncCron, тянущий заказы по внешним URL); features.md заявляет, что и то и другое «полное»
- Завышенное заявление о многоязычном поиске ES: CLAUDE.md заявляет «индекс ES содержит title/description на всех языках с весами по locale», но Products::toSearchableArray() индексирует только базовые одножзычные поля; заявленный в CLAUDE.md каталог app/search/ фактически не существует (Searchable встроен в модель)
- WebSocket-чат поддержки не реализован: только структура таблиц ChatSessions/ChatMessages (features.md честно признаёт «WS в разработке», согласованно, но это действительно не завершено), и у автомата заказов статусы «ожидает модерации (8)/возврат средств (6)» не имеют ни одного пути записи (нет процесса модерации, возврат — только admin executeRefund сразу к «средства возвращены (7)»)
- Тестовое покрытие узкое и расходится с документацией: всего 4 файла юнит-тестов (AUDIT-REPORT.md признаёт «нет интеграционных тестов/нет отчёта о покрытии»), нет интеграционных тестов контроллеров/заказов/платежей/промежуточного ПО; api.md 13.18 говорит, что экспорт возвращает CSV, в коде по умолчанию XLSX + CSV опционально; документированные в api.md 2.1 параметры фильтра min_price/max_price в ProductController::index не реализованы

### Риски
- В цепочке оплаты нет идемпотентности и покрытия событий: POST /api/payment/create без ключа идемпотентности — повторные запросы создают несколько записей «ожидает оплаты»; webhook обрабатывает только payment_intent.succeeded / PAYMENT.CAPTURE.COMPLETED, события refunded/failed молча игнорируются, опора на PaymentReconcileCron (ищет только записи старше 2 часов)
- Дрейф двух источников ставок расщепления: webhook и SettlementCron читают ставки соответственно из config('payment.gateway_fee.*') и config('cron.payment_gateway_fee_*') — два места независимого ведения; к тому же после создания PlatformSettlements(status=0) в webhook SettlementCron снова пересчитывает с дедупликацией по order_id — риск повторов и расхождения; расщепление — только комиссия платформы + комиссия шлюза, для supplier_amount нет процесса выплат, affiliate_amount всегда 0, мультивалютное расщепление и расчёты (docs/08-multi-currency-settlement) не замкнуты
- Свежее развёртывание — пустые данные + соответствие по умолчанию пропускает: бизнес-сиды отсутствуют полностью, в config/country.php blocked_countries по умолчанию пустой массив, kyc_required_countries только KR; перехваты запрещённых товаров/KYC в OrderController зависят от ручной конфигурации — при недоконфигурации всё полностью открыто
- Хрупкая зависимость поиска: при недоступности ES вся секция try/catch деградирует на MySQL LIKE, у scout нет очереди (config/scout.php sync.queue=false), индекс и многоязычный анализатор не покрыты CI — дрейф индекса неуправляем
- Пробелы финансовой точности и автомата: суммы заказов накапливаются через float round; возврат только целого заказа status=7 без частичного возврата; автомат Refunds 2(отклонено)/3(средства возвращены) переходит только по единственному пути AdminOpsController, нет пользовательской заявки на возврат и интерфейса модерации (этапы модерации/ярлыка в процессе возврата features.md 3.5 зависят от admin)

## 2. Админ-панель (admin/)

### Сводка текущего состояния
Админ-панель на webman-admin + LayUI/Pear Admin имеет полный мастер установки, RBAC-права, стек WAF-промежуточного ПО и каркас из 82 контроллеров/76 моделей, но бизнес-слой «имеет контроллеры, не имеет страниц»: из 67 контроллеров магазина 59 — чистые CRUD-заглушки только с привязкой модели, кроме трансграничной панели нет ни одного HTML-представления (клик по меню даёт 404), а ShopOrder/ShopPayment — фатальная ошибка при загрузке класса в PHP 8.3 из-за несовместимости сигнатур методов, меню заказов/платежей фактически неработоспособно.

### Реализовано
- 82 контроллера (15 системных + 67 shop) и 76 моделей (9 системных + 67 shop) существуют попарно с заголовками Copyright, пространства имён соответствуют plugin\admin\app\controller|model
- Общий CRUD-базовый класс Crud полностью реализует select/insert/update/delete и форматирование tree/select/normal, включая права на данные (dataLimit: personal/auth), фильтр inputFilter по белому списку полей из desc-структуры таблицы, хэширование паролей, точки расширения afterQuery/insertInput/updateInput
- Web-мастер установки InstallController реально работает: step1 создание БД + проверка конфликтующих таблиц + импорт корневого install.sql (117 таблиц) + генерация plugin/admin/config/database.php и thinkorm.php + генерация service/.env и admin/.env (случайные JWT/Hashids/AES/ADMIN_API_KEY) + перезагрузка SIGUSR1; step2 создание супер-администратора и привязка роли 1; importMenu рекурсивно импортирует config/menu.php в wa_rules
- Полная система прав: промежуточное ПО AccessControl + plugin\admin\api\Auth::canAccess (noNeedLogin/noNeedAuth/сопоставление правил ролей/супер-админ * wildcard/разделение 401 и 403), зависит от таблиц wa_roles/wa_rules/wa_admin_roles
- Стек промежуточного ПО соответствует features.md 4.2: SecurityMiddleware (erikwang2013/security-php SecurityGuard + защита входа от перебора 5 раз/300s + безопасные заголовки ответа), PlatformMiddleware (определение 8 платформ по UA), HashidsDecode/HashidsEncode (декодирование запросов и кодирование полей *_id ответов), AccessControl
- Структура меню config/menu.php (526 строк): 6 системных групп + 7 бизнес-групп «анализ данных/управление магазином/управление заказами/таможня и налоги/управление логистикой/управление маркетингом/управление цепочкой поставок», всего 27 пунктов меню магазина с весами/иконками/маршрутами
- Трансграничная панель ShopDashboardController + представление ECharts (тема Pear Admin, карточки KPI и 5 контейнеров графиков, ссылка на echarts@5.5.0 CDN)
- Утверждение возвратов ShopRefundController — один из немногих контроллеров с реальной бизнес-логикой: автомат 0 ожидает/1 одобрено/2 отклонено/3 средства возвращены, перед отметкой «возвращено» вызывает внутренний интерфейс service POST /api/admin/refunds/{id}/execute (авторизация X-Admin-Key, на service реально существуют AdminOpsController + AdminKeyMiddleware), при сбое запись в БД отклоняется
- Экспорт заказов ShopExportController: PhpSpreadsheet генерирует Excel (номер заказа/дата/статус/валюта/сумма товаров/скидка/доставка/оплаченная сумма), barryvdh/laravel-dompdf генерирует PDF коммерческого инвойса (с деталями, валютой, напоминанием о таможенной декларации)
- Модели единообразно на снежинкообразных первичных ключах (Base::boot creating автоматически генерирует string-тип ID), бизнес-модели объявляют таблицы erik_ и разделяют с service одно MySQL-соединение (plugin.admin.mysql)
- Базовые файлы i18n существуют: в admin/resource/translations пять языков zh_CN/zh_HK/en/ja/ko по 48 ключей
- Сопровождение качества и развёртывания: composer.json содержит phpunit ^12.5 и dev-зависимость php-cs-fixer, конфигурация admin/Dockerfile + docker-compose (порт 8788) полная

### Пробелы
- **Фатальный дефект (реально воспроизведён)**: ShopOrderController.php и ShopPaymentController.php при переопределении методов базового класса Crud имеют несовместимые сигнатуры (отсутствуют возвращаемые типы : array / : Response) — в PHP 8.3 фатальная ошибка при загрузке класса; меню «Список заказов»/«Платёжные записи» падает при первом же обращении и попутно роняет webman-процесс

- Блокирует запуск: ShopOrderController/ShopPaymentController — фатальная ошибка при загрузке класса (реально воспроизведено на PHP 8.3), два меню «список заказов»/«платёжные записи» при открытии сразу выдают ошибку, а фатальная PHP-ошибка заставляет весь резидентный процесс webman перезапускаться с ошибками

- Crud::selectInput возвращает 6 элементов, а select() разбирает только 5 ($page отбрасывается, пагинация зависит от глобальных параметров запроса Illuminate); doSelect не обрабатывает строковые операторы кроме like и другие граничные случаи; в сочетании с отсутствием тестов — высокий риск регрессий при последующих изменениях

## 3. Flutter-клиент (apps/flutter/)

### Сводка текущего состояния
Каркас Flutter-клиента полный (11 страниц, 11 маршрутов, таблица слов на 5 языках, три перехватчика Dio в соответствии с промежуточным ПО бэкенда), но состояние «демонстрационный уровень, который можно просматривать»: три торговых замкнутых цикла — оформление/регистрация/оплата — на бэкенде отклоняются 422/40001 из-за отсутствия address_id и человеко-машинной проверки PosterVerify, i18n подключён только на 1 странице, мультивалютность не проходит через API.

### Реализовано
- Технологический стек и инженерный каркас реально существуют: pubspec.yaml/lock фиксирует flutter_riverpod ^2.3.0, go_router ^12.0.0, dio ^5.3.0, responsive_framework, cached_network_image, flutter_secure_storage, shared_preferences, intl ^0.20.2; в lib/ 25 файлов Dart, каталоги шести платформ android/ios/macos/linux/windows/web полные
- GoRouter с 11 маршрутами (app_router.dart): /、/products、/product/:id、/cart、/checkout、/orders、/profile、/addresses、/login、/register、/order/:id — соответствующие 11 файлов страниц реально существуют
- Инфраструктура i18n: app_localizations.dart жёстко кодирует 5 языков (zh_CN/zh_HK/en/ja/ko) по 32 ключа перевода; locale_provider.dart через Riverpod StateNotifier + SharedPreferences персистит язык/валюту, localeProvider/currencyProvider зарегистрированы
- Перехватчики Dio в соответствии с промежуточным ПО бэкенда: _AuthInterceptor (Bearer token + при 401 вызов /auth/refresh с повтором), _LocaleInterceptor (заголовки Accept-Language + API-Version, соответствуют LocaleMiddleware/VersionRoute бэкенда), _PlatformInterceptor (заголовок X-Platform, соответствует PlatformMiddleware бэкенда)
- Контракт API-слоя согласован: ApiResponse{code,msg,data} и PaginatedData{list,total,page,per_page} соответствуют единому формату ApiResponse::success/paginate бэкенда; apiBaseUrl поддерживает переопределение через --dart-define, особая обработка 10.0.2.2 для эмулятора Android

### Риски
- Ключевая торговая цепочка на стороне Flutter неработоспособна: оформление (нет address_id + PosterVerify 40001), оплата (нет /payment/create), регистрация (PosterVerify 40001) — все три точки будут отклонены бэкендом; выпуск по текущему коду напрямую блокирует конверсию покупок
- Нет гварда входа + логика обновления 401 без дедупликации конкурентных запросов: одновременные множественные 401 будут конкурентно вызывать /auth/refresh (в api_client.dart нет блокировки), и при сбое refresh нет запасного выхода через logout — состояние токена может стать несогласованным
- Долгосрочное сосуществование двух систем i18n (таблица слов + ~66 жёстко закодированных) приведёт к смешанному языку интерфейса, новый текст будет сразу хардкодиться; обещание 5 языков и заявление docs/VERSIONS.md «интернационализация ✅» невыполнимы, затраты на переработку будут накапливаться
- Разрыв между мультивалютным отображением и фактической оплатой: интерфейс может переключаться на JPY/KRW, но цены по-прежнему отображаются по доллару и API считает по USD — суммы мультивалютных расчётов не сходятся, это риск согласованности транзакций
- Нет гейта Flutter CI, и flutter/dart analyze в этой среде из-за SDK только для чтения не может быть запущен и проверен: опора на ручной review 25 файлов — высокий риск регрессий компиляции/статики (исторические проблемы из docs/VERSIONS.md — конфликт intl, pending Timer — как раз без автоматической защиты)

## 4. HarmonyOS-клиент (apps/harmonyos/)

### Сводка текущего состояния
HarmonyOS-клиент (HarmonyOS NEXT API 12+, ArkTS + ArkUI) имеет компилируемый полный каркас из 9 страниц + ApiClient/AppState/ProductCard, все конечные точки API бэкенда и структуры ответов реально совпадают (в AUDIT-REPORT зафиксировано: 27 ошибок ArkTS исправлены, сборка успешна), но глубина функциональности остаётся «слоем отображения»: основная цепочка корзина-оформление оборвана (нет address_id), Profile — статическая оболочка, нет подключения мультивалютности/мультиязычности, нет тестов и CI, 99 артефактов сборки ошибочно в репозитории — в целом заметное отставание от Flutter-клиента.

### Реализовано
- Все 9 страниц ArkTS существуют и зарегистрированы в main_pages.json (Index/ProductDetail/Cart/OrderList/Checkout/Profile/Login/Register/Search), плюс EntryAbility, ApiClient, AppState, ProductCard — компилируется (подтверждено кэшем entry/build и записями об исправлениях M3 в AUDIT-REPORT.md, рейтинг B+)
- ApiClient инкапсулирует @ohos.net.http: GET/POST/DELETE, Bearer token, API-Version(2026-05-20), Accept-Language, заголовок X-Platform: harmonyos, декларативные интерфейсы QueryParams/RequestBody удовлетворяют ограничениям литералов ArkTS
- AppState-синглтон: token/locale/currency персистятся через @ohos.data.preferences (хранилище erik_shop), cartCount тянется расчётом /cart, logout очищает token
- Маршруты бэкенда и вызовы клиента совпадают один в один: /auth/login, /auth/register, /products, /products/{id}, /banners, /search, /cart(GET/POST/DELETE), /orders(GET/POST), /shipping/calculate, /payment/methods — все зарегистрированы в service/config/route.php и контроллеры существуют
- Структуры ответов согласованы с парсингом клиента: products/orders/search возвращают data.list (включая китайский маппинг status_text, поддержку sort=sales), cart возвращает массив items (title/image/price/quantity), shipping возвращает data.options, payment/methods выставляет только stripe/paypal

- Страница поиска реализует поиск по ключевым словам (/search?keyword=&per_page=40), счётчик результатов, пустое и загрузочное состояния, переиспользует ProductCard

- Страница деталей товара реализует загрузочное состояние, отображение главного изображения/заголовка/цены/описания, добавление в корзину (берёт первый SKU и вызывает POST /cart)
- Список заказов реализует Tabs-фильтр статусов (все/ожидает оплаты/отправлен/завершён → status 0/2/4) с загрузочным/пустым состояниями

- Страница оформления показывает товары заказа/варианты доставки (выбор Radio)/способы оплаты, считает сумму, поддерживает действие отправки

## 5. Безопасность и соответствие

### Сводка текущего состояния
Платформа имеет реальную и относительно полную реализацию WAF-детекции атак, JWT-пары токенов, AES-шифрования интерфейсов, шифрования полей Encryptable, обфускации Hashids, проверки подписи платёжных Webhook и управления ключами (22 теста пройдены), но у движка правил фрод-контроля, KYC и исполнительного слоя GDPR/CCPA только структура таблиц и CRUD админки, ключевая бизнес-логика отсутствует — несоответствие заявлениям «полное/✅» в docs/features.md и docs/VERSIONS.md.

### Реализовано
- WAF-детекция атак: SecurityMiddleware и service, и admin инкапсулируют SecurityGuard из erikwang2013/security-php v1.1.6, конфигурация config/plugin/erikwang2013/security-php/app.php — 31 детектор (28 block, 3 log: header_injection/ssti/nosql_injection), включая XSS/SQLi/XXE/SSRF/обход пути/загрузку файлов/CSRF/Host/DNS rebinding, плюс IP-чёрный список (5 раз/60s→бан 900s), безопасные заголовки ответа (nosniff/DENY/Permissions-Policy/скрытие Server)
- Защита от перебора паролей: на service счётчики Redis erik_brute:{ip}:{login|register} 10 раз/60s (SecurityMiddleware::checkBrute), на admin 5 раз/300s
- JWT-аутентификация: config/jwt.php (HS256, access 7200s/refresh 1209600s, issuer/audience/leeway), app/common/Jwt.php с fail-closed при пустом ключе (цепочка отката JWT_SECRET→JWT_SECRET_KEY), JwtAuth отклоняет токены не-access-типа, AuthController при регистрации/входе выдаёт пару токенов, refresh-конечная точка ротирует пару (зафиксирован firebase/php-jwt v6.11.1)
- AES-шифрование интерфейсов: app/common/Encryption.php (AES-256-CBC, случайный IV на каждый раз, base64(iv+шифротекст), проверка длины ключа 16/24/32 байта), EncryptionMiddleware поддерживает X-Encrypted:1 дешифрование запроса, X-Encrypt-Response:1/X-Encrypt-Fields шифрование полей ответа, пропускает /api/health, /api/ping, /apidoc, зарегистрировано последней ступенью глобального стека
- Шифрование полей Encryptable: 31 модель использует trait Erik\Encryptable\Encryptable (Users email/mobile, UserKyc real_name/id_number, UserAddresses, PrivacyRequests.email, PaymentGateways.api_key и т. д.), пароли через bcrypt(password+salt) с индивидуальной случайной солью на пользователя, $hidden предотвращает утечку при сериализации
- Обфускация Hashids: config/hashids.php + конфигурация плагина, HashidsHelper с fail-closed при пустой соли, промежуточные ПО HashidsDecode (параметры маршрута + автоматическое декодирование полей с окончанием _id) и HashidsEncode включены и в service, и в admin, контроллеры наружу возвращают кодированные ID
- Безопасность оплаты: StripeGateway проверяет подпись через Stripe\Webhook::constructEvent, PayPalGateway — через официальный /v1/notifications/verify-webhook-signature (нужен PAYPAL_WEBHOOK_ID); в PaymentController::webhook проверка подписи→идемпотентное обновление (атомарная защёлка статуса заказа=0 против двойного зачисления)→создание расщепления PlatformSettlements; create-интерфейс выставляет только реализованные stripe/paypal; в таблице erik_payments есть поле three_ds_status; интерфейс выполнения возврата из admin проходит AdminKeyMiddleware (X-Admin-Key, сравнение hash_equals)
- Управление ключами: .env.example/.env содержат JWT_SECRET/JWT_SECRET_KEY/HASHIDS_SALT/ENCRYPTION_KEY/ADMIN_API_KEY/STRIPE_SECRET_KEY и др., .env в .gitignore; Web-мастер установки (InstallController) генерирует случайные ключи через random_bytes; Jwt/Encryption/HashidsHelper при отсутствии ключей fail-closed
- Лимитирование и человеко-машинная проверка: RateLimitMiddleware — скользящее окно Redis ZSET (по умолчанию 60s/100 запросов, вход 60s/10, регистрация 300s/5, оплата 60s/5, оформление 10s/3, поиск 1s/10), PosterVerify защищает чувствительные маршруты регистрации/оформления/оплаты
- Тесты и инструменты качества: в tests/ 22 tests/45 assertions, реально ALL PASS (SecurityTest 12 + JwtTest 4 + ApiResponseTest 3 + RedisFacadeTest 3), phpunit.xml, phpstan.neon (level 5), .php-cs-fixer.php, .github/workflows/ci.yml (матрица PHP 8.3/8.4 + сервисы MySQL/Redis); в README зафиксирован 1 известный низкорисковый CVE от composer audit (firebase/php-jwt <7.0.0, ограничен jwt-webman ^6.0)

### Риски
- Блокировка по безопасности зависимостей: firebase/php-jwt v6.11.1 находится в зоне действия документированного CVE-2025-45769 (<7.0.0), жёстко ограничен erikwang2013/jwt-webman ^6.0 — обновление невозможно, это долго не закрываемая известная брешь (симметричное использование HS256 не затронуто, но нужно постоянно следить за апстримом)
- Слепые зоны покрытия детекции: header-детекторы csrf_origin/host_header/dns_rebinding/request_smuggling зависят от $_SERVER, в не-CGI среде Workerman возможны пропуски (признание в docs/security-review.md §5.1); IP-чёрный список хранится через file в sys_get_temp_dir — при перезапуске Docker теряется, между инстансами не общий, атакующий ротацией IP обходит (в конфигурации предусмотрено хранилище redis, но не включено)
- Брешь между заявлениями о соответствии и реализацией: по документации наружу заявлено «фрод-контроль полный/KYC полный/GDPR полный», фактически создание заказа проходит без какой-либо фрод-оценки (риск мошеннических заказов), KYC нельзя подать самостоятельно, запросы на удаление никто не исполняет — публичные обещания возможностей соответствия при этом образуют реальный комплаенс-риск
- Слабое управление ключами: мастер установки генерирует ENCRYPTION_KEY через bin2hex(random_bytes(16)) (32 hex-символа = 128 бит энтропии, не 256 бит), HASHIDS_SALT через bin2hex(random_bytes(8)) (64 бита энтропии); у ENCRYPTION_PREVIOUS_KEYS нет автоматизации ротации; изменение .env в резидентном процессе webman действует только после reload

- Каскадный риск отсутствия ключей/аутентификации в проде: compose запускается с плейсхолдерами по умолчанию (серия change_me) без замены, ES без аутентификации, Redis по умолчанию без пароля, порты сервисов полностью открыты — при неполной конфигурации .env выход в прод сразу раскрывает поверхность атаки 9200/6379/3306/80

- Риск достоверности данных при холостой работе внешних зависимостей: три cron — отслеживание логистики/правила соответствия/синхронизация заказов платформ — по умолчанию не выполняют никакой реальной синхронизации; если эксплуатация ошибочно считает «уже автоматизировано», будут тихие сбои: трекинг не обновляется, правила соответствия устаревают, заказы платформ пропускаются

- У подписочных покупок и AB-тестов нет серверного API (только таблицы + CRUD-контроллеры admin, в route.php нет соответствующих маршрутов); «мультиплатформенность: публикация товаров Amazon/eBay/Shopee/Lazada/Temu + агрегация заказов» не имеет реальной интеграции платформ, только PlatformOrderSyncCron тянет по общим URL (в PlatformListings нет бизнес-записи); WebSocket-IM не реализован, но VERSIONS.md помечает ✅ (features.md/README честно помечают)

### Риски
- Документация систематически раздувает пометку «полное» (мультиплатформенность, движок фрод-контроля, подписки/AB, четырёхлинейное расщепление, PDF инвойса, Klarna/Adyen, WS-поддержка) — для клиентов с коммерческой лицензией образуется разрыв между ожиданием поставляемых функций и реальностью, есть контрактный и доверительный риск
- После свежей установки базовые данные пусты (сиды не импортируются автоматически, мастер не запускает seeder) — таблицы core-данных countries/currencies/payment_gateway_methods без данных, списки товаров, способы оплаты, расчёт доставки/пошлин — главные цепочки из коробки неработоспособны
- Покрытие динамической документации API — только 2/38 контроллеров, у клиентов Flutter/HarmonyOS нет авторитетного основания для стыковки; статический docs/api.md и route.php несут риск дрейфа конечных точек (71 vs 73, плюс несогласованность схемы конвейера внутри features.md)
- Тестовое покрытие — только 22 юнит-теста (безопасность + JWT + ответы + Redis), 38 бизнес-контроллеров с нулевым покрытием, у admin нет тестов, нет интеграционных тестов и отчёта о покрытии — высокий риск регрессий при массовых рефакторингах/апгрейдах
- В БД payment_gateway_methods по-прежнему содержит строки нереализованных шлюзов klarna/adyen и т. п.: при ошибочном включении конфигурации фронтенд может их показать, но после оформления обработчика шлюза нет — в цепочке оплаты скрытая точка отказа
