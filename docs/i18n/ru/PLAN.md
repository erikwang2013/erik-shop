## 1. Общая оценка

Фундамент инфраструктуры Erik Shop прочен (117 таблиц, 39 контроллеров, реальные шлюзы Stripe/PayPal, стек безопасности WAF/JWT/AES, 22 юнит-теста пройдены), но основной торговый путь одновременно оборван на четырёх концах — service/admin/Flutter/HarmonyOS, около десятка заявленных в документации «полными» возможностей на деле являются только структурой таблиц или CRUD-заглушками, а гейты качества (PHPStan/интеграционные тесты/клиентский CI) существуют формально — в целом платформа находится на стадии **«каркас полный, замкнутых циклов нет, документация впереди кода»**. За 3-6 месяцев нужно сначала остановить кровотечение и замкнуть торговый цикл, затем добавить базу соответствия и качества, и наконец расширять инкрементальные возможности и свести документацию.

## 2. Пять глобальных проблем

1. **Основной торговый путь одновременно оборван на трёх концах** (подтверждается перекрёстно сервером/Admin/двумя клиентами): в service `OrderController::store` не считает купоны/доставку/пошлины/фрод-контроль (только суммирует подытог товаров); во Flutter и HarmonyOS при оформлении отсутствует `address_id`, запросы отклоняются PosterVerify 40001, оплата никогда не вызывает `POST /payment/create`; в admin `ShopOrderController`/`ShopPaymentController` из-за несовместимости сигнатур методов с PHP 8.3 падают при загрузке класса (Fatal). При текущем состоянии путь конверсии покупки полностью неработоспособен, меню управления заказами/платежами падает при первом же открытии.
2. **Документация систематически опережает код** (подтверждается в четырёх областях: документация/сервер/безопасность/соответствие): `features.md`/`VERSIONS.md`/`README` помечают движок фрод-контроля (RiskEngine), оплату Klarna/Adyen, четырёхлинейное расщепление, PDF коммерческого инвойса, подписочные покупки/AB-тесты, WebSocket-чат поддержки, мультиплатформенную публикацию как «полные/✅», тогда как на деле это только структура таблиц + CRUD admin или вообще ноль бизнес-реализации — для коммерческих клиентов это риск несоответствия ожиданиям и потери доверия.
3. **Отсутствие бизнес-сидов + пустой исполнительный слой безопасности и соответствия** (подтверждается сервером/развёртыванием/соответствием): `install.sql` содержит сиды только системных таблиц; countries/currencies/payment_gateway_methods/hs_codes/shipping_zones после свежей установки полностью пусты (ключевые интерфейсы из коробки возвращают пустоту); при этом `blocked_countries` по умолчанию пустой массив, фрод-контроль нигде не вызывается, у KYC нет точки подачи, GDPR/CCPA только регистрируются без исполнения — «из коробки пусто + по умолчанию пропускать» в сочетании с недостоверными заявлениями о соответствии.
4. **Бизнес-слой Admin — «есть контроллеры, нет страниц»**: 59/67 — чистые CRUD-заглушки без HTML-представлений, клик по меню даёт 404; маршруты kpi/chartData трансграничной панели и сигнатура json повреждены вдвойне; 40 контроллеров не привязаны к меню — UI управления магазином фактически неработоспособен, что серьёзно расходится с заявленной в документации «полной админ-панелью».
5. **Гейты качества существуют формально** (подтверждается тестами/развёртыванием/документацией): всего 22 юнит-теста покрывают 4 утилиты, бизнес-контроллеры/промежуточное ПО/модели не покрыты вообще; PHPStan по умолчанию 128M падает из коробки, у admin нет никакой конфигурации качества; в CI нет шагов phpstan/php-cs-fixer/composer audit и jobs Flutter/HarmonyOS; 99 артефактов сборки HarmonyOS ошибочно попали в репозиторий — любое слияние рефакторинга проходит без защиты.

## 4. Ключевые риски (обрабатывать в первую очередь)

1. **Отсутствие идемпотентности в цепочке оплаты + дрейф двух источников ставок расщепления**: повторные запросы payment/create создают несколько платёжных записей «ожидает оплаты», webhook обрабатывает только успешные события; ставки gateway_fee независимо ведутся в двух местах — риск дублирования и несогласованности в расщеплении.
2. **Риск доверия: документация опережает код**: движок фрод-контроля, Klarna/Adyen, четырёхлинейное расщепление, PDF инвойса, подписки/AB, WS-поддержка и ещё десяток заявленных «полными» пунктов на деле являются заглушками или CRUD-заглушками — для коммерческих клиентов это разрыв между ожиданиями поставки и реальностью.
3. **Пустые сиды свежей установки + соответствие по умолчанию пропускает**: интерфейсы countries/способов оплаты/доставки/пошлин из коробки возвращают пустоту; blocked_countries по умолчанию пустой массив, KYC только KR — при недоконфигурации всё полностью открыто.
4. **Гейты качества существуют формально**: всего 22 юнит-теста покрывают утилиты, PHPStan по умолчанию 128M падает из коробки, у admin нет тестов и конфигурации качества, в CI нет phpstan/composer audit/клиентских jobs — слияния рефакторингов не защищены.
5. **Открытые поверхности продакшен-промежуточного ПО**: ES без аутентификации и с открытым 9200, Redis по умолчанию без пароля, порты MySQL/сервиса открыты полностью — можно запустить в прод без полного .env.
